OpsFlow AI

A system for the team that handles customer problems, such as "I was charged but my order still says pending". It tracks each problem through fixed steps, works out what probably happened, suggests a fix, and waits for a manager to approve it.

Why I built it

Most of what I have built at work is private. I built OpsFlow AI in the open to put the backend patterns I use into one system anyone can read, run and try to break. It is a demonstration project, not a product with users.

I chose operations support as the subject because it needs every guarantee at once. A skipped step, a lost event or an unapproved refund each has a real cost.

The problem it solves

Most teams already handle these problems, with a ticket in a general tool, an engineer searching logs and a fix agreed in chat. That works until something goes wrong and nobody can say who decided what.

The usual way, by handWith OpsFlow
TrackingA ticket anyone can set to any statusA request that only moves through allowed steps; a skipped step is refused
Two people on one caseThe last save wins and the other change is lost silentlyThe second save gets 409 Conflict and has to reload
Finding out what happenedSearching logs in several systems and looking for the right wiki pageOne button collects the history, whether the events were delivered, and the closest runbook
Choosing the fixDepends on who is on shiftA recommendation from a fixed list of actions, with its evidence
Approving a risky fix"OK, go ahead" in a chat messageA manager approves in the system; an agent who tries gets 403
Telling other systemsA direct call that is lost if the other side is downAn event saved with the change and delivered when Kafka is reachable, handled once
"Who did this, and when?"Pieced together afterwardsAn audit trail of every step under one correlation id

One case, start to finish

  1. An agent creates the request. The change and its event are saved in one database transaction. CREATED
  2. The system classifies it as a payment problem, high priority. CLASSIFIED
  3. The agent presses Investigate. The system collects the request's history and events and finds the closest runbook. INVESTIGATING
  4. It recommends replaying the payment event. The policy says that action needs approval. PENDING_APPROVAL
  5. The agent tries to approve it and is refused with 403.
  6. A manager reads the evidence and approves. RESOLVED
  7. Every step is in the audit trail, and each change went to Kafka as an event.

One honest limit: approving records the decision and resolves the request. No payment system is connected, so nothing is replayed for real.

GuaranteeHowProven by

The AI step: retrieval, then a recommendation

The request text is turned into a vector by an embedding model, and pgvector returns the closest runbooks. Their text goes into the prompt with the request and the evidence, and a language model recommends one action. This is retrieval-augmented generation (RAG). Both models run locally, so there is no API key and nothing leaves the machine.

I measured it on a labelled set: 30 questions with the runbook that should come back, and 16 requests with the action that should be recommended, written the way a customer writes.

No model (word hashing, keyword rules)Embedding model and language model

Measured on a 4-CPU machine with no GPU, with all-minilm and qwen2.5:1.5b in Ollama. It is a small set and a small model. The model is still wrong one time in four, which is exactly why it only recommends and a manager approves.

What measuring it taught me

  • The load test found a bug my tests had missed. The request list failed on PostgreSQL when no search text was given. The in-memory test database had accepted the query.
  • It found two bottlenecks in my own design. The outbox published 25 events a second and took 653 seconds to clear its backlog. After two measured changes it clears in 18 seconds.
  • The AI evaluation found a readiness bug. The service reported healthy before its search index was built, so early searches returned nothing.
  • Kubernetes found a naming clash. The cluster injected a REDIS_PORT variable that the application read as its port setting, and the first deployment would not start.

What it is not

  • Not a product. It has no users, and approved actions are recorded, not executed.
  • Not an AI agent. The backend decides what evidence to collect; the model is asked once and only recommends.
  • Not scaled out. The outbox publisher runs as one instance. Running several needs row claiming first.
  • Not production Kubernetes. The manifests are tested on a throwaway cluster in CI; there is no Ingress or autoscaler.

The repository lists these limits too, with what I would do next about each.
