Edge

First stop is the edge. Nginx handles TLS, gives the request an ID and passes it on to the app container.

  • An ID on every request. When something breaks in production, the first thing I want is one ID I can search for in every service's logs.
  • Small images, quick deploys. Multi-stage Docker builds keep compilers and build tools out of the final image. When a deploy takes three minutes instead of twenty, people ship smaller changes, and smaller changes break less.

where I built this

OpsFlow AI · 2026 (public code): the whole stack (API, PostgreSQL, Kafka, Redis and the dashboard) starts with one Docker Compose command, and CI runs it that way on every push.

Freelance · 2025–26: I set up multi-stage Docker builds behind Nginx, and deploys went from about 20 minutes to 3.

Accenture · 2021–24: our Azure DevOps pipelines built, tested and shipped Docker images to Kubernetes.

Rate limiter

Next, the rate limiter. Every request spends a token. When a client runs out, it gets a 429 and a note saying when to try again.

  • Say no early. If a request is going to be refused anyway, I'd rather refuse it before it reaches the password hasher or the database.
  • Tell clients when to retry. A 429 with Retry-After lets well-behaved clients back off by themselves. When I'm the one calling someone else's API, I respect it too.

where I built this

OpsFlow AI · 2026 (public code): a rate limiter kept in Redis and updated by one Lua script, checked before authentication, with a lower limit on login.

Freelance · 2025–26: rate limiting and IP throttling in front of the login and the client APIs.

Public · task-management-api: a token-bucket filter that answers 429 with Retry-After. It has its own tests.

Auth

Then auth. The token gets checked, signature first, then expiry, then role. One service hands out tokens and the rest only verify them.

  • Keep security code together. On the freelance platform I moved auth into its own service. It's a small piece of code to review, and changing it doesn't ripple through everything else.
  • Role and ownership are two different checks. The role decides whether you can call an endpoint at all. Ownership decides whether you can touch that particular record.

where I built this

OpsFlow AI · 2026 (public code): JWT with five roles and a role check on every endpoint. Only a manager can approve an action; an agent who tries gets a 403.

Freelance · 2025–26: auth runs as its own service with JWT, RBAC, fine-grained permissions, encryption and audit logs. Splitting it out cut coupling by about 60%.

Accenture · 2021–24: Spring Security with JWT and role-based access on every endpoint.

Service

            
Now the business logic. The services don't keep state between requests, so any replica can answer, and handling more traffic means running more replicas.

          

          
          

            

              
    
                
  • Stateless services are easy to scale. If it doesn't matter which pod a request lands on, more capacity is just a higher replica count in Kubernetes.
    • 
                
  • Check input at the door, answer in one format. Bad input gets rejected where it enters the service, and every endpoint returns errors in the same shape, so clients only handle one format.
    •

Cache & database

            
Data that's read all the time comes from Redis. Everything else should hit an index, not scan the whole table.

          

          
          

            

              
    
                
  • Look at the query plan before adding hardware. Most of the slow APIs I've fixed were one missing composite index away from fast.
    • 
                
  • Cache on purpose. I cache data that's read a lot and changes rarely, and I decide up front what clears it.
    • 
                
  • Keep history as data. With Type-2 versioning every change is a new row, so you get an audit trail for free.
    • 
              

              

                
where I built this

                
OpsFlow AI · 2026 (public code): Flyway migrations, and runbook search on pgvector with an HNSW index.

                
Accenture · 2021–24: indexes, rewritten queries and Redis caching on PostgreSQL made our APIs 75–80% faster.

                
Freelance · 2025–26: MySQL query tuning, TypeORM indexes and caching got API responses under 100 ms. I also built a headless CMS with Type-2 versioning, which made content work about 90% faster.

Queue

            
Heavy work doesn't happen while the user waits. The API stores the file, publishes an event and replies. A worker picks it up from Kafka.

          

          
          

            

              
    
                
  • Reply fast, process later. The user gets an answer in milliseconds, and the processing can take its time.
    • 
                
  • Let the queue take the spike. A burst of traffic makes the queue longer instead of timing out the web servers.
    • 
                
  • Know the trade-off. Async means eventually consistent, and a consumer has to handle the same message twice without breaking anything.
    • 
              

              

                
where I built this

                
OpsFlow AI · 2026 (public code): a transactional outbox to Kafka. Events are marked as sent only when the broker confirms; the consumer handles each one once, and unreadable messages go to a dead-letter topic. Tested against a real broker.

                
Accenture · 2021–24: document uploads went to Amazon S3, and processing moved to Kafka and RabbitMQ consumers, on the platform with 10,000+ concurrent users.

    OpsFlow AI
    
            
    For the team that handles customer problems, like a payment that was charged but never confirmed. It tracks each problem through fixed steps, works out what probably happened, suggests a fix, and waits for a manager to approve it. Underneath: a request moves through fixed states with optimistic locking. Every change goes to Kafka through a transactional outbox and is marked as sent only once the broker confirms it; the consumer handles each event once and moves unreadable messages to a dead-letter topic. It also runs on Kubernetes: CI applies the manifests to a cluster, then kills the backend and database pods and checks both come back with the data. Load-tested on a 4-CPU machine: about 590 requests a second at a p95 of 188 ms, with all 23,622 events delivered and handled once. How it was measured ↗

    # Find every Team with no owner. Graph pages its results, so follow nextLink.
$uri = 'https://graph.microsoft.com/v1.0/groups?$select=id,displayName' +
       '&$filter=resourceProvisioningOptions/Any(x:x eq ''Team'')'
$report = do {
  $page = Invoke-MgGraphRequest -Uri $uri
  foreach ($g in $page.value) {
    $owners = Invoke-MgGraphRequest -Uri "https://graph.microsoft.com/v1.0/groups/$($g.id)/owners"

  }
  $uri = $page.'@odata.nextLink'
} while ($uri)

    example · Type-2 versioning in SQL
    

    -- An edit never overwrites: it closes the current row and adds a new one.
UPDATE page_versions
   SET valid_to = now(), is_current = false
 WHERE page_id = $1 AND is_current;

INSERT INTO page_versions (page_id, body, edited_by, valid_from, is_current)
VALUES ($1, $2, $3, now(), true);

-- "What did this page say on 1 Feb, and who changed it?"
-- is now a query, not a backup restore.
SELECT body, edited_by FROM page_versions
 WHERE page_id = $1
   AND valid_from <= '2026-02-01'
   AND (valid_to IS NULL OR valid_to > '2026-02-01');
