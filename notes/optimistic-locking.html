Engineering note · data consistency · 4 min read

Two people save the same task at once

Alice and Bob open the same task. Alice changes the title and saves. A minute later Bob, still looking at the old version, changes the status and saves. Without protection, Bob's save quietly wipes out Alice's change. Nobody gets an error. That's a lost update.

Two ways to stop it

  • Pessimistic locking: lock the row when someone opens it, and make everyone else wait. Safe, but people keep a task open for minutes, and locks held that long block others and can deadlock.
  • Optimistic locking: don't lock anything. Remember which version you read, and when you save, only succeed if it's still that version.

Real conflicts on a task are rare, so I went optimistic: no waiting in the normal case, and a clear error in the rare one.

How it works

The task has a version number that JPA increments on every update:

Task.java
@Version
private Long version;
see it in the repo ↗

Every update has to say which version it's based on. If the client doesn't send one, that's a 400, because an update without a version can't be checked. If the version is stale, the service refuses:

TaskService.java
if (request.getVersion() == null) {
    throw new IllegalArgumentException("version is required when updating a task (optimistic locking)");
}
// ...
if (!request.getVersion().equals(task.getVersion())) {
    throw new ObjectOptimisticLockingFailureException(Task.class, task.getId());
}
see it in the repo ↗

One exception handler turns that into 409 Conflict with a message telling the client to reload. Behind that check, Hibernate adds WHERE version = ? to the actual UPDATE, so even two saves arriving at the same millisecond can't both win.

The test replays the race

ApiIntegrationTests.java
update(alice, taskId, 0L).andExpect(status().isOk()).andExpect(jsonPath("$.data.version").value(1));
// A second client still holding version 0 must not overwrite the first client's change.
update(alice, taskId, 0L).andExpect(status().isConflict());
see it in the repo ↗

What the client has to do

A 409 isn't a crash, it's a question: "things changed, what now?" A UI should reload the task, show what's different and let the user save again. You can try it on my portfolio: in the Live API, run "Concurrent edit" and you'll get the 409 with the current and the stale version in the response.
