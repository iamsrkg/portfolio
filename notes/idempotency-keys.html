Retries are easy. Retrying safely isn't.

A client sends "charge invoice #1042". The request times out. Did the charge happen? The client can't tell, and if it simply retries, the customer may pay twice.

A timeout is not a "no"

When a request times out, three different things could have happened: it never reached the server, it failed on the server, or it succeeded and only the response got lost on the way back. From the client's side these look identical.

For some requests that's fine. GET, PUT and DELETE are idempotent by design: doing them twice leaves things the same as doing them once. POST is not. "Create a charge" twice means two charges. That's exactly where retries do damage, and retries are everywhere: HTTP clients, load balancers, message consumers, users pressing the button again.

The idea: give the operation a name

The client generates a unique key for each operation (not each attempt) and sends it as an Idempotency-Key header. The server remembers the first response for that key. A retry with the same key gets the stored response back, and the work doesn't run again.

  • Same key, same request: replay the stored response, marked with Idempotent-Replayed: true.
  • Same key, different request: 422. That's a client bug, and guessing which request it meant would be worse.
  • No key: the request runs normally, with no protection.

This is what I built into the Live API on my portfolio:

playground.js · the Live API
const idemSlot = idemKey && `${user ? user.sub : 'anonymous'}:${idemKey}`;
const fingerprint = `${req.method} ${pathname} ${(req.body || '').trim()}`;
const seen = idemSlot && IDEMPOTENCY.get(idemSlot);
if (seen && seen.fingerprint !== fingerprint) {
  throw new HttpError(422, 'IDEMPOTENCY_KEY_REUSED', 'This Idempotency-Key was already used with a different request.');
}
if (seen) {                                 // a retry: replay, don't redo
  headers['Idempotent-Replayed'] = 'true';
  status = seen.status;
  body = seen.body;
} else {
  const res = await r.handler(ctx);         // first time: do the work
  status = res.status;
  body = res.body;
  if (idemSlot && status < 300) IDEMPOTENCY.set(idemSlot, { fingerprint, status, body });
}

Two details matter. The key is scoped to the user, so one customer can't replay another's response. And only successful responses are stored: if the first attempt failed, the retry should really try again.

What changes in production

The demo keeps keys in memory, which is enough to show the behaviour. A real service needs a few more things:

  • Durable storage with an expiry. Keys go in the database or Redis with a TTL (24 hours is common), so a retry after a restart still finds them.
  • Atomic "claim the key, then do the work". Insert the key with a unique constraint in the same transaction as the work. Otherwise two copies of the same request arriving together can both pass the "not seen yet" check.
  • A request still in flight. If a duplicate arrives while the first is running, answer 409 ("in progress, retry shortly") instead of starting it twice.
  • Consumers too. Kafka and RabbitMQ deliver at least once, so a consumer can see the same message twice. The same idea applies there: record processed message IDs and skip repeats.

Try it

On the portfolio's Live API, press Retry a POST. It sends the same "charge invoice #1042" request twice with one key, like a client retrying after a timeout. Both answers are 201, but the second is a replay: same task, Idempotent-Replayed: true, and the trace shows the database insert ran only once. Then change the body and send it again with the same key to get the 422.

It pairs with the database switch on the same page. Retries, timeouts and a circuit breaker keep a service answering when things break; idempotency keys make sure those retries don't do the work twice.
