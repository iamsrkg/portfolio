Why someone else's task is a 404, not a 403

In my task API, if Bob asks for one of Alice's tasks, he gets 404 Not Found, exactly what he'd get for a task that doesn't exist. That's on purpose.

The problem with 403

The obvious version fetches the task by ID, then checks whether you're allowed to see it and answers 403 Forbidden if not. It looks correct, but it leaks something: a 403 means "this exists, you just can't have it". Task IDs in URLs get guessed, copied and logged. With a 403, anyone can find out which IDs belong to real records in other people's accounts. In a multi-tenant system, that alone is information about other customers.

There's a second problem too: fetch-then-check means every endpoint has to remember to do the check. Forget it once and you have a data leak.

Put the tenant in the query

So the check isn't a separate step. The only way to load a task is a query that already contains "and it belongs to you":

TaskRepository.java
@Query("""
        select t from Task t left join t.assignee a
        where t.id = :id and (t.project.owner.id = :userId or a.id = :userId)
        """)
Optional<Task> findVisibleById(@Param("id") UUID id, @Param("userId") UUID userId);

If the task isn't yours, the query returns nothing, and the service turns "nothing" into the same 404 as a missing ID. There's no code path where someone else's task gets loaded into memory and then rejected.

When 403 is the honest answer

This doesn't mean 403 never happens. If you're the assignee of a task, you can see it, but only the project owner can edit or delete it. You already know the task exists, so hiding it would just be confusing. That case gets a real 403.

  • Can't see it: 404, same as if it didn't exist.
  • Can see it, not allowed to change it: 403.

Proving it

A rule like this is easy to break later, so there's a test for it. It checks GET, PUT and DELETE on another user's task, and compares the result with a random ID that never existed:

ApiIntegrationTests.java
mvc.perform(get("/api/tasks/" + taskId).header("Authorization", bearer(bob)))
        .andExpect(status().isNotFound());
// ... PUT and DELETE get the same 404 ...

// Same answer as for a task that doesn't exist at all.
mvc.perform(get("/api/tasks/" + UUID.randomUUID()).header("Authorization", bearer(bob)))
        .andExpect(status().isNotFound());

The trade-off

Debugging is a little harder: "not found" can mean two things, so support staff can't tell from the status code alone. I think that's the right price. The logs still carry the request ID and the user, so the real reason is one search away, just not in the response.
