Why my rate limiter runs before authentication

In my Spring Boot API the order of filters is: tag the request with an ID, then rate limit, then authenticate. The order matters more than it looks.

Password checks are slow on purpose

Passwords are hashed with BCrypt, which is designed to be slow, around a tenth of a second per check. That's what makes stolen hashes hard to crack. But it also means every login attempt costs the server real CPU time.

If rate limiting happens after authentication, someone hammering the login endpoint makes the server run BCrypt on every single attempt before anything says no. The protection arrives after the expensive part. So the rule I follow: reject cheaply first. A request that's going to be refused anyway shouldn't reach the password hasher or the database.

SecurityConfig.java
// Cheapest checks first: tag the request, then rate limit, then authenticate.
if (rateLimitEnabled) {
    http.addFilterBefore(new RateLimitFilter(rateLimitCapacity, rateLimitRefillPerSecond), JwtAuthenticationFilter.class);
    http.addFilterBefore(new RequestIdFilter(), RateLimitFilter.class);
}

A token bucket per client

Each client IP gets a bucket of tokens (20 by default) that refills at a steady rate (5 per second). Every request takes one. That allows short bursts, like a page loading several things at once, but not a sustained flood. When the bucket is empty the answer is 429 Too Many Requests with a Retry-After header, so a well-behaved client knows exactly how long to wait instead of retrying in a tight loop.

RateLimitFilter.java
synchronized (bucket) {
    bucket.refill(capacity, refillPerSecond);
    allowed = bucket.tokens >= 1;
    if (allowed) {
        bucket.tokens -= 1;
    } else {
        retryAfterSeconds = (long) Math.ceil((1 - bucket.tokens) / refillPerSecond);
    }
    remaining = (long) Math.floor(bucket.tokens);
}

Two details that are easy to miss: the lock is per bucket, not global, so one busy client doesn't slow everyone else down. And idle buckets get evicted once there are more than 10,000 clients tracked, so the map can't grow forever.

What this doesn't solve

  • More than one server. The buckets live in each instance's memory. With three instances behind a load balancer, a client effectively gets three buckets. The fix is a shared store: a Redis counter with a short expiry, or rate limiting at the gateway.
  • Everyone behind one IP. An office or a mobile network can put many real users behind one address. For logged-in traffic, limiting per user (from the token) is fairer. Per-IP is the right tool in front of the login, where there's no user yet.

For a single service, an in-memory bucket in front of auth is simple, fast and easy to test, and it covers the case that actually costs money: floods against the login.
